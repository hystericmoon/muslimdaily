# Adwam (formerly Muslim Daily)

Native Android app `id.haho.adwam` (formerly `id.haho.muslimdaily`; the Kotlin packages keep that
name). Kotlin 2.3,
Compose, Hilt, Room, DataStore, Glance. Sideloaded through GitHub Releases.

## Content rules (non-negotiable)

- Never write or generate religious content: Arabic, translations, virtues or sources come only
  from `content/source/*.csv` via `tools/build_content.py`. See `docs/content-guide.md`.
  One exception, approved by the owner: the Latin transliteration is derived from the sourced
  Arabic by the fixed rules in `tools/transliterate.py` (never written by hand or by a model).
- Sahih/hasan narrations only. Show a count only where the Sunnah gives one.
- The owner has no reviewer: check every imported row yourself (grade, not a duplicate, a dua
  the reader says, translations matching the Arabic) and leave out any row that fails, with the
  reason in the importer. Never fix a source's text by hand. See "Checking imported content" in
  `docs/content-guide.md`.
- No gamification (streaks, points, badges). Fully offline. WCAG AA.

## Build and test

```
# once per haho-design version (see docs/architecture.md, "Design system"):
#   cd ../haho-design && git checkout v<hahoDesign> && ./gradlew publishToMavenLocal
export ANDROID_HOME=/opt/android-sdk
python -m unittest discover -s tools          # content pipeline
./gradlew :app:lintDebug :app:testDebugUnitTest
```

- Screenshots in `docs/screenshots` are recorded on CI's Linux runner, and CI fails when a render
  no longer matches. After a UI change, run the **Screenshots** workflow on your branch (Actions →
  Screenshots → Run workflow, or `gh workflow run screenshots.yml --ref <branch>`): it commits the
  new shots and re-runs CI. Start it right after pushing a UI change instead of waiting for CI to
  fail. Shots recorded locally (`recordRoborazziDebug`) differ in fonts and
  anti-aliasing, so use them to preview only and never commit them.
- Screenshot tests run on Robolectric pinned to Indonesian (`id-rID`); new shots are
  numbered 100+ in `RoutineScreenshotTest`.
- Every new string goes in both `values/strings.xml` (Indonesian, default) and
  `values-en/strings.xml`. Lint fails on unused resources.
- Icons are generated: add to `tools/icons/build_icons.py`, don't hand-write drawables.
- The Adwam mark (launcher foreground and themed icon, notification glyph) is
  generated by `tools/brand/build_mark.py`; logo files and rules are in `docs/brand/`.
- `UserDatabase` changes need a Room auto-migration and the exported schema in `app/schemas/`.
  Data the user creates must also go into `BackupRepository` (bump its `VERSION`, keep old
  backups restorable).

## Release

- Stable by default: minor for features, patch for fixes; beta only when the owner asks. Say
  which version you will ship before merging. Merging a `versionName` change publishes a GitHub
  Release. Steps: the `release` skill (`.claude/skills/release/`), `docs/release.md`, `docs/beta.md`.
- Feedback/report email: `muslimdaily.reportEmail` in `gradle.properties`.

## Workflow

Work on a branch, run lint and tests, push, open a PR to main, merge once CI is green.

Standing approval from the owner: merge your own PR (merge commit) as soon as CI is green and it
is mergeable, without asking. Ask first only when the PR carries a risk:

- it changes `versionName` (merging publishes a release to users),
- it changes shipped religious content (`content/source/*.csv`, `content/*.json`, `content/audio/`),
- it changes `UserDatabase`, `BackupRepository` or anything that could lose user data,
- it adds a permission, network access or a new third-party dependency,
- a review comment or a test result you could not resolve is still open.

## Sessions

One session at a time. Start by reading `docs/handover.md` (short by design; the archive is
`docs/history.md`, searched, not read whole). Before you stop, or when the conversation is
getting long, update it and merge it with your PR or on its own. The handover is the only
backup: the owner clears each session, and anything not merged to main is lost.

Standing instruction from the owner (3 Nov 2026): sessions alternate between Opus and Sonnet,
and the owner starts and clears them. Don't start or archive sessions yourself.

- When the owner asks for work, say first which model it needs (rule below). If this session
  is on the other model, say so before starting. If a Sonnet session finds the task needs
  Opus, stop, write what you found into the handover, and say so.
- When the owner says they are clearing the session: follow the `session-clear` skill (update
  and merge the handover, then "Safe to clear", the next model and its prompt).
- Opus: religious content (imports, grades, translations, sources); audio cuts and checks;
  `UserDatabase`, `BackupRepository` or anything that could lose user data; features across
  several modules; bugs of unknown cause; decision pages that need research.
- Sonnet: UI polish, copy and strings, generated icons, screenshot re-records, version bumps
  and releases with known contents, bugs of known cause, docs and handover, non-breaking
  dependency bumps, carrying out a written plan the owner already chose.
- The test: if a wrong call could put wrong religious content in front of users or lose their
  data, Opus; if it is specified and a mistake shows in review or screenshots, Sonnet.

More: `docs/architecture.md`, `docs/design-tokens.md`, `docs/accessibility.md`, `docs/fonts.md`.

## Token guard

- Be concise. Lead with the answer; no restating the question, no recap of what was just done.
- Route mechanical work (renames, formatting, summarizing, scraping, bulk find-and-replace) to a sub-agent with `model: "haiku"`. Keep judgment and design work in the main session.
- Exception: never hand a Haiku sub-agent anything that touches religious content or user data (see "Sessions" for which work needs Opus).
- Never suggest `/compact` as a cost-saving measure. Suggest `/clear` between unrelated jobs instead.
- Keep the model and effort fixed for the whole session. Switching mid-session invalidates the prompt cache, so start each session on the model its task needs (see "Sessions").
- Project skills hold the repeated procedures and load only when used: `content-import`, `audio-recut`, `release`, `session-clear`. Use them instead of re-reading the long docs; read a doc section only when the skill points to it.
- Searches across many files or docs (e.g. "where is X handled"): use the Explore sub-agent and keep only its conclusion.
- Noisy install, build and test output is trimmed by `.claude/hooks/trim-output.py` to the error lines plus the last 30 lines. If you need the full log, rerun the command with `> /tmp/log.txt` and grep that file.
